# App quality verification matrix — September 25, 2026

This is the verification inventory for the quality pass starting at `bd75611`. It accounts for **all 70 route modules**, **all 20 admin navigation destinations**, **13 configurable public widget types**, **6 resource renderer types**, and **40 managed-function entry points** present at that baseline. Route patterns represent all records using that template; listing a pattern does not establish that every record is valid.

This document records what needs to work, the implementation behind it, the available regression evidence, and what still requires a deployed environment. **A source inspection, a test file existing, a successful build, and an actual browser/provider test are different forms of evidence.** No route is labelled “passed” simply because its implementation or tests were inspected. The release report supplies execution results and newly repaired defects.

## How to use the matrix

For each action, verify the useful outcome, not merely that the control responds. Exercise success, empty data, invalid input, rejected request, timeout, double-click, retry, cancelled action, stale response, browser Back/Forward, and navigation away while a request is pending where applicable. Check keyboard operation, focus/feedback, mobile layout, and whether refreshing preserves the correct durable state.

- **L — Local:** meaningful component/unit/server-handler checks can run with controlled fixtures; browser-only controls can run locally.
- **B — Backend:** a disposable authenticated database/storage environment is required to prove persisted writes, reloads, roles and concurrent sessions. A mock success is insufficient.
- **P — Provider:** an external service or provider sandbox must prove the complete outcome. Do not treat a redirect, accepted request, or provider configuration flag as payment, delivery, or indexing success.
- **M — Known pending backend:** prior read-only inspection found a required shared-backend update absent. Recheck migration history before release; do not silently reinterpret the unavailable state as an empty result.
- **A — Administrator:** verify anonymous, authenticated non-admin, expired-session, and admin behavior independently.

Test names below identify existing evidence to run, **not proof of complete coverage**. Prefixes: `L/` = `src/lib/__tests__/`; `C/` = `src/components/__tests__/`; `A/` = `src/components/admin/__tests__/`; `CFG/` = `src/config/__tests__/`; `P/` = `src/pages/__tests__/`; `DB/` = `scripts/tests/`. The exact suffix is shown for each file. Tests frequently cover a subset of the row, so the action checklist remains necessary.

Existing component mocks and isolated database contracts provide substantial evidence but do not prove browser→deployed API→storage/database integration.
4. **Verify actual auth recovery and session lifecycle.** Dedicated test admin/non-admin accounts; password recovery email exchange; expired tokens; sign-out-other-devices; revoked/expired sessions during save; network loss. Do not change the owner's real password or revoke their sessions as a QA shortcut.
5. **Expand direct shared-widget and failure-path coverage.** Baseline source review found `PageShareBar` silently reset its copied state after clipboard rejection, and root stale-chunk recovery accessed `sessionStorage` without a guard. The current quality pass is repairing these with targeted regressions; use the final release results to establish completion. News search/topic history and failed pagination retry handling are also being repaired in this pass. These originated as source findings, not newly executed browser failures.
6. **Separate app routes from duplicate legacy handlers.** Confirm/unsubscribe and machine-readable feeds have app and managed implementations. Test the exact deployed URL, status, headers, token behavior and public data boundary rather than assuming a shared-helper test proves both adapters. This pass added `L/newsletterConfirmRoute.test.ts`: ten direct app-adapter tests using controlled database responses. Actual deployed confirmation, delivery and legacy-handler parity remain integration gates.
7. **Evaluate paid automation in a bounded staging run.** Run one real generation of each article/resource/guide kind and a representative news/opportunity pipeline with a fixed budget; prove cancellation, duplicate job protection, partial failure, evidence requirements and concurrent edits. Model output still requires content review; passing schema validation does not establish useful or accurate copy.
8. **Browser checks must cover states, devices and record shapes.** At minimum: desktop keyboard, 390px and 320px; all six resource shapes; all offer modes; empty/long/malformed data; focus/errors; network interruption; every dialog's cancel and submit; Back/Forward and record-to-record navigation. Existing tests do not establish screen-reader usability, cross-browser parity, performance budgets, load capacity or security penetration-test results.
9. **Close operational gaps before asserting “everything works.”** Search Console import currently has a documented partial-snapshot risk; planner measurement is excluded by the current coordinated allowlists; legacy render-page needs the planner path. Treat these as explicit unfinished operational features, not as conversion or UI failures already fixed.
