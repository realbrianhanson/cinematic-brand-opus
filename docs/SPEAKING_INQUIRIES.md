# Speaking inquiries

The speaking page captures event inquiries in the private admin inbox at `/admin/inquiries`. The homepage has a short speaking invitation linking to that page. An inquiry is not a newsletter subscription, booking confirmation, or payment. Optional transactional email confirms receipt without promising availability or a response deadline.

## Deployment and setup

1. Apply `20260919200000_speaking_inquiries.sql`, `20260924010000_speaking_notifications.sql`, and `20260924011000_transactional_email_suppression.sql` and record the migrations.
2. Deploy `submit-speaking-inquiry`, `process-speaking-notifications`, and the updated `resend-webhook` with their shared helpers. `verify_jwt = false` is intentional: visitors need no login to submit; the notification worker independently requires the existing cron secret, service role, or a verified administrator. The Resend webhook requires its existing verified signature. Database inquiry storage works without email configuration.
3. Publish the frontend, then use **Admin → Speaking inquiries → Accept inquiries** when someone is ready to monitor the inbox. `site_settings_private.speaking_inquiries_enabled` defaults to false, including on new PushTen installations. Enabling a production owner is an explicit owner action, not a member-template migration side effect.
4. Set the brand’s speaking email link to a real monitored address for the direct-email fallback. The form saves independently of that fallback address.

5. Before enabling email, configure the existing `RESEND_API_KEY` server secret, a verified `site_settings.newsletter_from_address`, valid `newsletter_reply_to`, and an HTTPS `site_url`. No new email provider is introduced. In **Speaking inquiries → Email notifications and follow-up**, set a monitored owner notification address or leave it blank to use the brand reply-to address. Save **Enable inquiry emails** only when ready to send. New installations default to disabled; this change does not enable production sending by itself.
6. The portable migration does **not** install a schedule. In `setup/speaking-notifications-cron.sql`, set `project_url` to the current project's verified Supabase URL, confirm its Vault `CRON_INVOCATION_SECRET` and deployed worker, then execute the script in that project's SQL editor. It refuses the placeholder and non-Supabase URLs. The installed schedule makes no HTTP request while inquiry emails are disabled. Pause with `SELECT cron.unschedule('speaking-notifications-15min');`. Without a scheduler, initial submission attempts still run, but retries and reminders require authenticated worker invocation.

When enabled, each **new** inquiry atomically creates exactly one owner notification, one organizer acknowledgement record, and one owner reminder eligible after 48 hours. At most one acknowledgement is queued per normalized email address in 24 hours; further acknowledgements show Cancelled, while every inquiry is still saved and its owner notification is queued. Known suppressed addresses never receive acknowledgements. This decision is serialized by a database advisory lock so concurrent submissions cannot bypass the cooldown. The reminder is cancelled if the inquiry is no longer New when claimed; all unclaimed mail for Spam is cancelled. Mark inquiries Contacted after replying. Existing pre-enablement inquiries are not backfilled. Disabling pauses pending mail; re-enabling resumes that queue. A message already in flight may finish. The owner address and sender are frozen for a delivery at its first provider attempt, so changing configuration does not alter a retry.

The admin panel shows queued/processing counts and failures requiring review. Individual inquiries show each email's status and retry eligibility. **Accepted by email provider** means Resend returned an ID; it does not assert inbox delivery. New inquiries older than 48 hours also show **Follow-up needed** even when email is disabled. A worker cannot send while settings or the provider key are unavailable; queued records remain visible, and the worker returns `configuration_required: true`. Check these settings if mail stays queued.

Submission success only depends on durable inquiry storage. Email provider failure cannot turn a saved inquiry into a form failure. A transactional acknowledgement contains no visitor-supplied text or links, preventing the form from forwarding arbitrary content to a third party. No recipient is added to a marketing list. Verified Resend bounce/complaint callbacks persist in the private `transactional_email_suppressions` table even when the address has never subscribed to the newsletter. The same atomic callback also suppresses an existing newsletter subscription; it never creates one. Duplicate or out-of-order events do not weaken a complaint. Failed storage returns HTTP 503 so Resend retries the event. The worker checks this table and legacy newsletter suppressions before every send, including the frozen original recipient on retries. Configure the existing `RESEND_WEBHOOK_SECRET` and ensure bounce/complaint events are enabled in Resend. Suppression records are service-only and included in the empty-remix bootstrap guard.

The private outbox uses database leases, frozen payloads, stable Resend idempotency keys, and backoff beginning at five minutes. Concurrent workers and exact form retries do not duplicate mail. Retries stop after six provider attempts, or before the 24-hour provider idempotency window expires. Uncertain outcomes move to Needs delivery review. Verify in Resend and contact the organizer manually if necessary; there is deliberately no blind resend button for an uncertain result. A saved lease with no receipt after a worker interruption is retried using the exact original payload/key. Private payloads and provider receipts are never exposed to the browser or logs.

## Data and access

The `speaking_inquiries` table stores contact name/email, event name, timeframe, format, audience, message, administrative status, private notes, and timestamps. A server-generated primary ID is separate from the random client request ID. Anonymous visitors have no table access. Non-admin signed-in users cannot read or change inquiries. Admins can read and update only `status` and `admin_notes`; contact data, idempotency identifiers, and submission timestamps cannot be edited through the admin client. Only the server submission function inserts new records. There is no browser-side delete operation.

The private intake setting is covered by the existing administrator-only private-settings policies. Changing it does not change automatic publishing, newsletter sending, or any other configuration.

## Submission behavior

- JSON is bounded while streaming, before allocation; contact fields are trimmed and validated, email is normalized, and text lengths are limited.
- Durable rate limits share the existing atomic database limiter with a distinct `speaking:` namespace. IP addresses and email addresses are hashed before becoming rate-limit keys. Limits are 30 requests per IP and 8 requests per email per hour. Limiter failures fail closed.
- The hidden website field gives obvious bots a neutral acknowledgement without storing an inquiry.
- The form keeps the same UUID for retries with unchanged details after an uncertain response. The database serializes identical request IDs, compares the normalized payload hash, and acknowledges a retry without adding another record. A different payload with the same request ID is rejected without revealing inquiry data. Existing matching retries remain acknowledged if intake was paused after the original write.
- A successful response is sent only after a stored inquiry or confirmed matching retry. Database internals and contact details are not logged or included in failure responses.
- Form failures preserve the entered values. Buttons prevent duplicate in-flight submissions; confirmed success receives keyboard focus. Safe direct email remains available as a fallback.
- Admin edits compare `updated_at` to avoid overwriting a change made in another window. Conflicts preserve the notes in the editor.

## Verification

`npm run test:database` includes an isolated PGlite suite covering intake and mail opt-in defaults, atomic outbox deduplication, exclusive leases, frozen retries, stale receipt rejection, reminder cancellation, expiry limits, table grants, administrator restrictions, and ordinary-user isolation. Unit/component tests cover input validation, escaped email rendering, acknowledgements without submitted content, mocked provider idempotency/uncertainty, safe email links, confirmed success, retry identity, duplicate clicks, safe admin rendering, and save failures/conflicts. Production QA must not create fabricated inquiries or send messages. Tests never call the live email provider.

## Backend contract

`submit-speaking-inquiry` accepts `POST` with JSON: `request_id` (UUID), `name`, `email`, `event_name` (required); `event_date`, `event_format` (`in_person`, `virtual`, or `undecided`), `audience`, `message`, and `website` (honeypot). It returns HTTP 200 `{ "accepted": true }` after acceptance. No lead ID or submitted personal information is returned. Errors have `{ "error": "visitor-safe message", "code": "..." }`: 400 `invalid_input`, 415 `invalid_input` for other content types, 409 `request_mismatch`, 429 `rate_limited`, and 503 `unavailable`. Other methods return 405; OPTIONS is allowed for CORS.

The service-only SQL RPC is `public.submit_speaking_inquiry(_request_id uuid, _payload_hash text, _name text, _email text, _event_name text, _event_date text, _event_format text, _audience text, _message text) RETURNS boolean`. Success and exact retries return `true`. Reusing a request ID with another payload raises `speaking_request_mismatch` (SQLSTATE 22023). Paused intake rejects new requests with `speaking_inquiries_disabled` (SQLSTATE 55000); an already stored exact retry still succeeds. Remaining database failures are mapped to the generic unavailable response.
