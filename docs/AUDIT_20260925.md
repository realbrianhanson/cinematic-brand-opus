# Website and funnel audit — September 25, 2026

This release improves the offer builder, public browsing, and administrator reliability. It follows the owner's instruction to deliver through GitHub into Lovable preview and leave final publishing for later. It does not send newsletters, submit inquiries, buy anything, invoke paid generation, change live offer records, apply database migrations, or deploy managed functions.

## Coverage and evidence

- Inventoried the route, component, library, migration and function surfaces. The repository has 69 route files, 40 edge-function entry points and 86 migrations. Focused source review covered public discovery/rendering, funnel authoring and commerce contracts, authentication, configuration, content operations, media, speaking, newsletter, measurements and publishing.
- Crawled **402 public page URLs**: 370 sitemap/known entries plus 32 additional internal news/access links. All returned HTTP 200. The 401 content/discovery pages passed title, description, canonical and single-H1 checks. `/offer-access` intentionally omits a canonical and is explicitly `noindex, nofollow, noarchive`; it is an access utility rather than an indexable content page. No duplicate titles were found in the initial 370-page set. This was a server-rendered structural check, not a fact check of every article.
- Read-only browser inspection covered home, shop/offer journeys, `/admin/offers/new`, overview, audience, inquiries, conversions, queue, publishing lists, generation, media, setup, configuration, account controls, niches, formats, categories, widgets, redirects and performance. Initial loading screens were not counted as successful data reads. No destructive/save/send controls were exercised against live data.
- Local browser checks confirmed PushTen's new mobile action is visible at approximately y426–482 on a 390×844 viewport, focuses the existing offer control, and introduces no horizontal overflow. The free-offer form becomes enabled after hydration and its mobile jump also focuses the form area. Resource search submission and Back restore the correct URL/input. No lead or order was submitted.
- A local development hydration warning was traced to a password-manager extension injecting a `data-lastpass-icon-root` node. The form recovered and enabled; this is recorded separately from application errors, not hidden as a clean console result.
- Live schema inspection found RLS enabled on all 64 public application tables. Existing privacy caveats and infrastructure hardening limits are in the admin/backend report; RLS presence alone is not proof of universal authorization correctness.
- Dependency audit returned no reported advisories. Independent code, TypeScript and database reviews were completed. Review found one stale-editor regression, which was repaired and independently approved before release.

Detailed source coverage and bounded findings: [public experience](AUDIT_PUBLIC_20260925.md), [funnels](AUDIT_FUNNELS_20260925.md), [admin/backend](AUDIT_ADMIN_BACKEND_20260925.md).

This is a broad, risk-based audit with repository-wide checks. It is not a claim that every branch of every file was executed, that all historical statements are verified, or that future conversion performance is guaranteed. Live financial transactions, real email delivery, paid AI generation, destructive actions, load testing and a penetration test were outside this preview release.

## Backend deployment still required

Read-only inspection confirmed that these already-committed migrations are absent from the live database:

1. `20260923140000_newsletter_truth.sql`
2. `20260923150000_admin_overview_truth.sql`

Their absence explains the observed overview, audience and newsletter history failures. The preview changes make the prerequisite clear; they cannot create the missing server functions.

The newsletter migration adds nullable error/status columns, administrator-only functions, delivery state handling and historical status corrections. It sends nothing by itself but changes future delivery/retry behavior. The overview migration adds read-only administrator reporting functions and an index; its ordinary index build can block writes briefly. Both passed isolated database tests and independent database review, but both affect the shared live backend immediately. They remain unapplied under the preview-only instruction.

When releasing the backend, compare migration history first and apply only these missing updates, recording their successful versions. Deploy the matching `send-weekly-newsletter` implementation and the changed `build-silo-links`, `generate-pillar` and `score-content-quality` functions, including their shared modules. Verify administrator reads, authentication and failure paths without sending mail or creating orders. Do not replay the entire older deployment runbook blindly.

Pushing GitHub code is not evidence that managed database functions or edge functions have deployed. Publishing the frontend alone will not repair these missing backend prerequisites.

## Highest-value next work

1. **Complete the backend release above.** This restores real dashboard/audience/newsletter operations and activates the staged link/scoring repairs.
2. **Prove one complete offer journey in payment-provider test mode.** Exercise checkout success/cancellation, webhook retry, fulfilment, access recovery, upsell purchase and refund reconciliation. Existing isolated tests cover these contracts; this audit did not make a real purchase. External PushTen checkout remains `https://go.aiforbusiness.com/get-pushten`.
3. **Measure customer outcomes before optimizing percentages.** Separate external clicks, registrations and confirmed paid outcomes. Reconcile verified provider records through the existing import path. The observed traffic is too small and includes admin/testing visits to justify a conversion-lift claim.
4. **Build offer-specific case studies from approved proof.** Show the starting problem, actual implementation, supported result, constraints and a relevant next step. Keep exact attribution and evidence; do not invent typical earnings or urgency. The reusable testimonial notes are not automatically published into the empty proof library.
5. **Add real order bumps, one-click upsells and decline branches as a commerce feature.** Current native commerce supports a single next-offer chain with a separate checkout. True one-click charges, multi-branch downsells, subscriptions and split testing need explicit payment consent, idempotency, refund/state handling and reporting. A new button label does not implement those features.
6. **Run focused experiments after measurement works.** Start with the promise, relevant proof near the action, one clear primary action and offer-specific FAQ. Define the success metric and avoid announcing a winner from a handful of visits.
7. **Finish the lower-priority polish backlog.** Resource typography/contents/printing, persistent news filters, category pagination at scale, consistent unsaved-change protection in older editors, serialized link rebuilding, and real-user performance measurement are detailed in the focused reports.
